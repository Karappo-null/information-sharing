# 開発方針と変更手順

最終更新: 2026-08-30

## 役割

- 仕様はプロジェクトオーナーが決定する。
- Codexは、決定済みの仕様を実装する。
- 現在の実装は、将来の仕様に合わせて変更・置換できるMVPとする。

## 実装前の進め方

仕様が不足している場合、Codexは実装を始める前に次を行う。

1. 不足している仕様を指摘する。
2. 選択肢と、それぞれのメリット・デメリットを説明する。
3. 推奨案がある場合は、その理由を説明する。
4. プロジェクトオーナーが決定するまで、その部分を実装しない。
5. 変更するファイルと変更内容を簡潔に提示する。
6. 承認後に実装し、lint・buildなど適切な確認を行う。

## 明示的な承認が必要な仕様

以下は、プロジェクトオーナーの明示的な承認なしに決めたり実装したりしない。

- データベース構造
- User / Topic / Post / Commentの関係
- 認証方式
- ユーザー権限、管理者権限、RLS
- Topic / Post / Commentの作成・編集・削除権限
- 公開範囲、グループ・参加者の設計
- 画面構成や重要なUI/UX仕様
- 通知
- ファイル・画像アップロードの仕様
- 後から変更すると大きな影響が出る仕様

## 技術的な提案

Codexは、実装方法、保守性、安全性、テスト方法などの技術的な提案を積極的に行う。ただし、提案が製品仕様を新たに決める場合は、実装前に承認を得る。

## MVPの優先順位

- 最小構成で実際に使うことを最優先にする。
- 将来の可能性だけを理由に過剰な設計・実装をしない。
- 将来の大幅な作り直しにつながる技術的な問題は、実装前に説明する。
- 実際の利用で必要性が分かった機能から追加する。
